# 产品化工作流

## 目录

1. 用户边界
2. 阶段状态
3. 单一事实源
4. 增量重建
5. 截图能力适配
6. 发布契约

## 1. 用户边界

普通用户只参与两次集中选择：一次性登记事实、截图方式。若名称/版本/权属/日期/发表状态或申请范围仍有冲突，再呈现一张合并确认卡。业务理解、源码清单、分页、格式和修复属于 Agent 工作。

## 2. 阶段状态

系统临时运行区的 `workflow-state.json` 保存环境、项目分析、业务理解、基础信息、申请表、源码、截图、手册、代码、渲染、验证和发布阶段。每阶段记录输入哈希、输出哈希、完成时间和信息。输出仍存在且哈希一致时跳过；输入变化时只让依赖阶段失效。运行区由项目绝对路径和交付目录生成稳定键，不写入项目目录。

## 3. 单一事实源

临时运行区的 `application-facts.json` 是所有正式材料的唯一登记事实源。业务表述来自 `business-understanding.json`，但不得覆盖已确认登记事实。申请表、手册、代码页眉、文件名和报告只从这两份模型派生。

## 4. 增量重建

- 改名称/版本：重建申请表、手册、代码页眉、PDF和报告；
- 补截图：重建截图清单、手册、手册PDF与报告；
- 修改业务功能：重建手册、申请表功能字段、源码选择与报告；
- 仅手工编辑DOCX：覆盖前保存到历史版本；不得静默丢失修改；
- 回滚：读取最近 `snapshot.json`，校验备份哈希后恢复。

## 5. 截图能力适配

浏览器或 Computer Use 是 Agent 工具层，不固化到单一平台。输出统一为 `screenshot-index.json`：稳定ID、路径、标题、章节、功能、角色、URL/窗口、动作、断言、尺寸、时间、SHA-256、质量状态和诊断。Computer Use 先写 `computer-use-session.json` 收据，再由确定性脚本生成索引。平台能力不足时切换用户截图，不伪造文件。

## 6. 发布契约

所有产物先进入系统临时运行区。只有真实 DOCX/PDF、代码分卷、来源追溯、`state=captured` 的截图索引、一致性报告和哈希均可重新打开验证时，才原子复制到“正式资料”并标记发布完成。成功后清理交付根目录中的任何旧式工作目录，只保留“正式资料”。主动跳过截图允许在临时运行区生成带占位符草稿；等待截图、截图失败和空列表均阻断正式发布，且不撤下上一份已验证正式材料。
